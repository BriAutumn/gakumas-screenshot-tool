# 单编成模拟和候选比较

双击项目根目录的 **launch-simulation.cmd**（或 launch-simulation-web.cmd），自动打开本地网页。页面沿用 GKTools 的橙色导航、左侧编成/右侧分布与历史比较布局，直接复用已固定的原引擎、数据和本地卡图；网页界面是本项目的独立实现，没有整站安装 Next.js、登录或数据库服务。源码BSD许可和来源在页面底部保留。

左侧可选择场地、填写属性和支援加成，点击卡片/道具替换，卡片弹窗可设置自定义强化。支持导入完整GKTools链接或JSON；“从记忆库选择”只读已归档的可用记忆，按当前场地计划筛选主记忆，再按相同角色和计划筛选副记忆。

点击“模拟”后显示真实直方图、均分、中位数、标准差和详细统计。候选可逐个命名并“加入候选”，然后同场批量比较。历史中点击记录可查看分布、载入编成、导出结果；点击☆保存。最近20条普通记录及星标记录保存在当前浏览器本地，清除浏览器数据会清除这些记录，重要结果请导出JSON或分数CSV。不同浏览器和不同端口的历史彼此独立。

服务只绑定127.0.0.1，默认端口8765；关闭启动窗口或Ctrl+C停止。整个运行过程离线，无CDN/在线图片请求。旧桌面窗口仍可用 `.venv\Scripts\python.exe simulate.py gui` 打开。

先体验可选择 `examples/simulation/original.loadout.json` 与 `examples/simulation/without-customization.loadout.json`：第一个来自已有 URL 示例，第二个是明确移除副记忆中卡片117的 `31x1` 强化的对照，不是新识图结果。两者都是场地160。

## 命令行

在 C:/gktool 打开 PowerShell：

```powershell
# 单个完整编成，多次真实模拟
.venv\Scripts\python.exe simulate.py compare examples/simulation/original.loadout.json --trials 1000

# 多候选比较，输出完整每次分数、配置、统计和版本信息
.venv\Scripts\python.exe simulate.py compare examples/simulation/original.loadout.json examples/simulation/without-customization.loadout.json --trials 1000 --seed 610397104 --output work/simulation/comparison.json

# 禁用缓存；每候选最多300秒，可自行调整
.venv\Scripts\python.exe simulate.py compare examples/simulation/original.loadout.json --trials 1000 --no-cache --timeout 300

# 仅启动本地网页服务（不自动打开浏览器），或更换端口
.venv\Scripts\python.exe simulate.py web --no-browser --port 8765
```

Ctrl+C 取消当前 worker，输出保留已经完成的候选，状态为 cancelled，退出码130。普通完成为0；部分候选失败或输入错误为1。某个编成被拒绝时，其错误会保留在报告里，其余合法候选继续运行。不同场地不能混排，应按场分别比较。

输入是现有 `Loadout` v1 JSON，四项属性是已合成后的编成属性，支援加成为比例（0.0472=4.72%），两组各6卡、4个道具。未知强化 null 会拒绝；确认无强化才用空字符串。引擎检查实体ID、强化适用性、角色/计划及场地，不能直接把单份记忆当完整编成。

## 从记忆库合成明确主副记忆

模拟模块通过 SQLite mode=ro 读取，只接受 reviewed 或 auto-resolved，人工审核优先，不初始化、不迁移、不写回结果库。

```powershell
# 替换为想使用的结果库目录（目录内应有library.sqlite3）
$libraryPath = 'data/captures/20260918-161240-dc783ee0/processing/20260919-215053-0c578609/memory-library'
.venv\Scripts\python.exe simulate.py memories --library $libraryPath

# 从上一条列表选两个明确的持有记忆ID；必须相同角色和计划
.venv\Scripts\python.exe simulate.py compose --library $libraryPath --main 主记忆ID --sub 副记忆ID --stage 160 --support-bonus 0.0472 --output work/simulation/my-loadout.json
.venv\Scripts\python.exe simulate.py compare work/simulation/my-loadout.json --trials 1000
```

普通竞技场合成规则直接对应同版本上游 `LoadoutContext.setMemory`：主记忆四项属性100%，副记忆四项各20%并分别向下取整（包含体力）；只使用主记忆4个道具；主副各提供一组卡片和强化。相同角色的不同偶像版本可以组合，计划需相同。场地和支援加成必须明确填写。生成结果可再用现有 GKTools URL 导出做人工核对。

## 如何看成绩

- 平均分：该候选所有实际试跑的算术平均，保留小数；网页显示值可能四舍五入。
- 标准差：样本标准差，表示单次成绩波动。只有1次时未知，显示“-”，不能当成零波动。
- 标准误：JSON 中的 standard_error，等于样本标准差/√次数，用于了解均值采样误差。
- 排名仅按样本均值，不代表已证明最佳。增加次数、换种子可以检查稳定性；不会进行自动组合搜索或跨三场分配。

每个候选使用相同初始种子，但行动和随机数消耗可能不同，因此不能把对应第N次当成同一抽牌条件。显式设种子调用上游原生 `resetRand`，只在固定引擎/数据/Node/输入下承诺复现。默认网页使用随机数，未经同步种子的网页单次成绩不会与这里必然一致。

缓存位于 `work/simulation/cache`，键包含完整输入、次数、种子、Node版本及引擎/数据/worker文件散列；读取前校验原文件和缓存内容，版本或内容变化会失效。只缓存完整成功结果，报告会标出 cached。可以使用 --no-cache 强制运行。

## 全库主副组合搜索与排行榜

网页下方「全库排行榜」使用当前编辑区的场地、支援加成与种子。选择最新可用库，点击「统计组合」查看组合数，再点击「开始全量搜索」。本次默认库为 `vision-20260919-05`：447份可用舞台回忆，全部对应原始采集编号；S46第1舞台有4,144个有序组合。主副互换分别计算，不允许同一持有副本同时占两个位置；相同角色、相同计划的不同版本可以组合。没有修改识别库或原始截图。

- 所有有效主副组合先模拟100次。复测包含总榜前30、各角色前3，以及均分±2标准误范围与这些入选边界重叠的组合；这些组合另跑2000次，使用原种子 XOR `0x9e3779b9`。筛选不是理论最优或显著性保证。
- 总榜列出各组合，角色榜每个角色保留最佳组合，可展开其全部组合。两个阶段分榜，按均分排序，展示中位数（对比弹窗）、标准差、标准误、与第一差距及次数。搜索未完成时标记暂定。
- 可勾选2–4组对比主副卡组、强化、属性和统计；可载入编辑、查看完整分布、保存至已有历史、导出榜单CSV。每个场地独立运行，不包含跨三场阵容分配。
- 主副编号沿用 `session.json` 的 `ordinal`，以原图路径和SHA256共同对应采集记录；相同图像的不同持有副本不会仅按图片哈希混为一份。编号不是游戏唯一ID，也不是入手日期。
- 「回忆封面」展示同次采集的已选中回忆原画面，可展开完整列表截图对照位置和日期。记忆库选择弹窗也能直接查看主副封面。缺少来源或校验失败会明确显示不可用。

搜索保存在 `work/simulation/searches/<id>/`。`manifest.json` 固定本次候选输入、来源库、编号、引擎文件版本和配置；`screen/`、`refine/` 保存每组完整成绩；`state.json` 每约5秒及停止时原子保存进度。刷新页面会重接已有任务；重开服务后可以继续。已成功的候选不会重跑，意外退出后最后少量未写进检查点的候选可由成功缓存恢复。引擎文件版本不同则拒绝续跑，需建立新搜索。失败项可重试，并在页面单独列出。

批量搜索使用持续运行的本地Node worker，每个候选独立重置随机种子。连续请求的成绩与独立进程一致；取消或失败会终止worker，恢复时重新启动。原始上游引擎和数据文件保持不变。

排行榜展示已改为与历史比较模块一致的横向箱线图：每页使用统一刻度，箱体为25%–75%分位，竖线为中位数，圆点为均分，横线为最低到最高分。图形直接读取该组合保存的完整分数，不从均值或标准差推算分位数；点击「直方图」查看单组详细分布。


### 分层复测规则 v1（2026-09-20）

新建搜索写入配置 `refine_policy=adaptive-character-v1`。未带此字段的旧搜索继续使用原来的总榜30+每角色3+接近项规则，续跑不改变已启动任务的规则。第1场旧搜索已完成133组复测。

新规则固定以100次初筛总榜第30名（不足30则末名）的「均分−2标准误」为边界。角色最佳组合的「均分+2标准误」达到该边界即有竞争力：选该角色前3及接近第3名的组合，按初筛均分取前15封顶。未达到边界但达到边界90%的角色复测前2，否则前1。可用组合少于名额时全选。旧的总榜前30不再额外突破角色上限。

初批复测全部结束后，若弱势角色某组合的复测均分超过其原初筛均分+2初筛标准误，且复测均分+2复测标准误达到上述固定边界，将该角色提升为有竞争力并补测。已测项保留，总名额仍不超过15；新增项完成后再检查，直到没有新增。每组2000次、独立复测种子和缓存规则不变。该筛选是计算预算分配启发式，不是最优或显著性保证。各角色档位、名额和补测标记写入检查点及排行榜。

验证：33项相关测试通过，含三档分配、15组上限、晋级补测、没有达到边界不补测、真实两阶段与取消续跑。


### 五轮初筛试验 v1

新搜索默认配置 `screen_policy=five-rounds-20-v1`：按全库顺序每组跑20次，累计20/40/60/80/100次，完成全部5轮后才开始2000次分层复测，不提前淘汰。第r轮种子为 `(base_seed+(r-1)*0x6d2b79f5) mod 2^32`，每组同一轮使用相同种子；不同编成不保证相同抽牌。累计100次不等同于旧连续100次随机序列。

首轮逐组展示20次成绩；其后轮次未结束前保留上一轮完整榜，保证比较样本数相同。完整成绩保存在 `rounds/1..5/<candidate>.json`，榜单快照在 `snapshots/20..100.json`。暂停续跑复用已完成分段，不重跑已完成轮次。旧搜索未带screen_policy，仍使用原100次流程。

轮次表展示前30保留数、上一轮前30的平均绝对名次变动、各角色最佳组合变化、模拟复测入选名单增减。最终复测完成后，额外报告各轮入选名单对“已复测前30”的覆盖数；这是受最终复测候选范围限制的回顾，不能证明没有漏掉未复测强组。总榜/角色榜仍按累计均分排序，分布图按请求次数读取对应轮次的完整成绩。


### 角色均衡复测 v2（2026-09-20，当前默认）

新搜索采用 `refine_policy=character-balanced-v2`，替代上文 v1 的名额分配。每个角色以初筛最佳组合参与角色榜，以角色榜第3名的均分−2标准误为边界（不足3个角色取末名）。最佳组合的均分+2标准误达到边界的角色，复测本角色前3及接近第3名的组合，最多15组；其余角色保底前3，可用组合不足3则全选。复测后的晋级补测仍保留。一个角色占据大量总榜位置不会挤占其他角色的保底名额或改变角色参考榜的席位。

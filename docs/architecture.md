# 架构与验证边界

0.5 增加与识别规则独立的素材采集层：`Windows 客户区截图/输入 → 界面状态检查 → 原子会话进度 + 带卡槽的原图 → 后续离线处理批次 → 独立结果记忆库`。采集模块不导入卡片 ID 模型或强化规则；只用本地布局和日文 OCR 检查制作专用文字与弹框。`capture/windows.py` 是用户独立运行的 Win32 适配器；`capture/runner.py` 是可模拟测试的状态流程；`capture/process.py` 在无游戏窗口时重复处理原图。具体边界和操作见 [capture.md](capture.md)。

新增的持有记忆流程：`同一记忆的多页详情 → 字段合并 / 来源记录 → SQLite 记忆库 → 人工核对 → [后续] 主副组合与整队搜索`。
它保存单份 Memory，不把 6 张卡补成 12 张，也不把列表缩略图当成完整 Loadout。细节见 [memory-library.md](memory-library.md)。

增加支路：`卡片浮动详情 → 本地日文 OCR → 两次缩放读取 / 完整字段规则匹配 → 显式绑定现有记忆与卡槽 → 自动填写强化字段`。这是字段级证据，并非整份记忆自动核验。规则受卡片与效果数据内容哈希约束；未知、不完整或冲突不产生空效果。详见 [card-detail.md](card-detail.md)。

```text
Screenshot
    ↓ 布局配置（当前是显式裁剪预设）
OCR + ONNX 卡片候选 + 普通道具模板 + 同图重复卡 / 强化标记辅助
    ↓
Recognition report + Draft（未知项为 null）
    ↓ 人工核对，补场地 / 支援加成 / 自定义
Loadout v1 JSON
    ├── GKToolsAdapter → URL → 网页手动模拟
    └── LocalSimulator → [未实现] Node worker → engine + data
                                                   ↑
                                          [未实现] updater
```

识别层不拼 URL；适配器不读取图片。`scan` 返回含 provenance 的待核对报告，`reviewed_loadout` 只接受完整且明确核对过的草稿。
原来的 `Recognizer` / `pipeline.run` 人工标注接口保留；自动扫描器返回的是更早阶段的候选报告，不冒充已经完整的 Loadout。

## 当前实现

- 布局配置按原图测量，识别前统一缩放。检查比例、可读数字与卡片区域；这只是有限布局校验，并非通用界面检测。
- OCR：RapidOCR 关闭检测与角度分类，分别读取放大的原始和加白边数字区域。不同处理结果冲突时该数字保留未知。
- 卡片：上游 64×64 RGB / CHW 模型；同一 ID 的美术变体概率求和，只保留候选，分数不等同校准后置信度。
- 重复卡：先确认灰色角标区域，再用卡面中央的颜色相关性与主卡比对；要求相似度和领先幅度同时达标。效果不随卡片 ID 复制。
- 强化：由上游 592/593 图标差分提取通用“+”图形，仅在有明确正向图形证据且候选中存在对应强化卡时修正；不能普遍保证强化判定正确。
- 道具：舞台道具图标的中心与全图误差组合；近似均匀灰色区域单独判为空槽。初测发现 ONNX 道具模型会高分误判，故不参与当前候选生成。
- 图像报告不根据截图哈希或 fixture 内容查表。哈希只用于素材验证与记录关联。
- GUI：识别在后台线程运行，通过队列回到 Tk 主线程更新。重新识别期间停用导出，识别失败时保留未就绪状态。
- 导出：检查场地类型、ID、舞台道具模式、允许的自定义效果和等级。缺失 / 未核对效果阻止导出；编辑字段会清除旧链接与核对勾选。

固定道具不写入普通道具槽，参照上游 `simulatorLoadout.js` 的四槽普通道具行导入行为。需要用户选对场地，不能由固定道具图案反推赛季。
本版保持 `url` 的标准库直接转换能力，它是给已核对数据使用的底层命令，不强制走 GUI 核对流程。

## 验证

真实 fixture 的可见数字和 ID 与上游图标分别核对。测试覆盖原图、等比例放大的 JPEG、交换主卡位置、灰色重复卡、强化候选、空白图 / 错误比例拒绝。
此外测试 URL 原样例、JSON 校验、自定义未知状态、非法 ID / 效果、GUI 核对后导出和修改后的旧链接失效。
临时合成图片仅用于扰动与拒绝测试，不伪装成额外的真实游戏截图。

目前有一张竞技场编成截图，以及同一份独立记忆的两张总览详情、一张列表定位图和一张卡片浮动详情；尚未建立跨设备 / 跨赛季识别准确率。未对网站运行结果或本地模拟分数进行验证。

## 数据与 D 阶段

识别资产固定在 `assets/recognition/manifest.json` 的提交与 SHA-256，加载时检查哈希。图标初次导入时也与上游 Git blob hash 比对。
清单用于防止资源混用或损坏，不是独立的签名分发系统。
Python 3.12+ 的识别依赖在项目虚拟环境内，基础 URL 工具仍支持 Python 3.11+。

Node worker、协议版本、请求 ID、随机种子、超时与统计仍留待 D 阶段；不翻译上游引擎。
更新默认采用 engine/data 配套版本，只有验证兼容的组合才允许单独更新数据。未来安装使用暂存、回归验证、原子切换与可回滚目录。
当前 `configs/upstream.lock.json` 仍标记模拟器未安装，与已经存在的识别资产清单是两件事。
